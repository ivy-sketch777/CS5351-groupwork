## AI component and cost optimization

### Role and authority boundary

Member 3 owns the AI extraction, student guidance, counsellor-summary, and application token-control components for REQ-FR-002, REQ-FR-005, REQ-FR-006, REQ-INV-002, REQ-INV-004, and REQ-COST-001. The extractor returns advisory medical facts through the shared `ExtractionResult` Pydantic contract. It has no authority to determine eligibility, make the policy decision, route a final case, or write an approval/rejection state. Those actions belong to deterministic policy, core workflow, or authorized human review.

### Extraction, prompt, and factual validation

The versioned extraction prompt requests hospital name, consultation date, recommended rest duration, and diagnosis. It treats the supplied certificate text as untrusted evidence, forbids eligibility decisions and unsupported inference, and requests `null` for missing or ambiguous facts. Each field carries `derived=True` and a confidence value.

The application validates the response locally rather than trusting prompt instructions alone. The decoder rejects malformed JSON, duplicate or unexpected keys, wrong field types, invalid confidence values, and fields without the required derived marker. A second source-grounding check accepts a value only when it matches the unique value on a supported labelled source line; dates must be valid ISO dates and the `Issue date` label is not treated as a visit date. Unsupported or ambiguous values are cleared, and low-confidence values are not returned as usable facts. The `confidence` number is model-reported and is not a calibrated accuracy guarantee.

The validator is intentionally conservative: it does not yet support arbitrary certificate layouts, every date format, image/PDF extraction, or document-authenticity verification. Those require separately reviewed preprocessing and validation. Security/core callers must authorize access, sanitize and redact text, and meet the provider's data-handling requirements before model invocation.

### Guidance and summaries

Student-facing missing-material guidance and counsellor summaries use deterministic templates, avoiding extra LLM requests for these functions. Guidance is constructed from a caller-provided `PolicyDecision`, its actual missing items, and fired rule IDs. The summary formats explicitly supplied display name, duration, dates, derived diagnosis, and document-completeness status; it does not infer completeness or recommend approval. End-to-end invocation, display authorization, audit persistence, and status transitions remain integration responsibilities.

### Cost strategy and provider compatibility

REQ-COST-001 sets an average target of at most 1,500 tokens per request, a 3,000-token total hard limit, and no model call for eligible simple requests. For a supported provider, the extraction path reserves 300 output tokens and permits generation only when an input-token count for the complete request plus that output reserve is at most 3,000. It fails closed on unavailable, invalid, or oversized preflight counts, and checks provider-reported usage after generation. The latter is a consistency check; it cannot prevent already-consumed tokens. Simple-request eligibility is supplied by the caller, and guidance and summary formatting are deterministic.

The CityU gateway accepted the tested Chat Completions route, but rejected strict JSON Schema response formatting with HTTP 400. Two tested token-count routes returned HTTP 405. No exact or defensible count for this model alias and complete chat framing has been verified. Consequently the ordinary CityU extraction path raises `TokenBudgetUnavailable` during preflight and returns empty derived fields without generation. This is a deliberately fail-closed, **incomplete production integration**; REQ-COST-001 is not complete for this provider. No character/byte proxy or mock count is represented as a real production token count.

### Verification evidence and limitations

The current checkout was rechecked for this document review: all 37 Member 3 AI offline tests passed using mocks. These cover the contract, missing/conflicting or unsupported fields, grounding, low confidence, malformed responses, skipped requests, preflight budget branches, errors, and the CityU adapter's blocked preflight. The live-test package was separately verified to collect; test collection is not live execution.

An earlier, explicitly experimental evaluation used five synthetic labelled-text certificates via direct experimental generation rather than the production preflight path. All five were reported to pass their expected-value checks. Provider-reported total usage was 337, 351, 348, 340, and 360 tokens, an average of **347.2 across those five cases** and a maximum of 360. The missing-diagnosis case returned no diagnosis, and the issue-date case returned the visit date. These results are historical evidence for this small set, not a population-wide average, a guarantee for future requests, or proof that the production 3,000-token hard cap works.

Code review identified limitations in the historical five-case evaluator: it prints each expected-value comparison but does not assert `passed` at the end, its validation helper omits production low-confidence filtering, and failed attempts can read stale experimental usage metadata. It also continues later cases after provider errors. These gaps remain uncorrected in the reviewed checkout. The historical printed comparisons and usage records are retained as limited experimental evidence, not as proof that the evaluator reliably fails every incorrect extraction.

During this document review, the full offline suite again stopped during local test collection because the active Python environment lacked FastAPI. The current `requirements.txt` does list FastAPI and contains no merge-conflict markers; markers had been found in a different earlier snapshot. A declared dependency is not proof that it is installed in the active environment. No full-suite pass is claimed here.

## Personal reflection

As Member 3 of MedLeaveAssist, I was responsible for medical-information extraction, student guidance, counsellor summaries, and token-control components. This project helped me understand that effective AI-assisted development requires a controlled engineering process rather than simply generating working code. I used Cursor and OpenCode within a plan-and-approval workflow, reviewed proposed changes, and restricted modifications to my assigned paths to protect the shared schema and teammates’ modules. The main requirements remained stable: AI could extract information but could not approve leave, determine eligibility, or invent medical facts. Nevertheless, implementation exposed ambiguities concerning provider compatibility, evidence validation, and token accounting. The CityU gateway rejected interfaces used by the original adapter, whereas an experimental Chat Completions path successfully returned JSON. This required adapting the technical approach while preserving the original authority boundaries. Another important clarification concerned the difference between measuring tokens after generation and enforcing a budget before sending a request. Five synthetic cases reported an average of 347.2 tokens, but this small sample could not demonstrate that every future request would remain below the 3,000-token limit. The review process rejected fabricated preflight counts and retained fail-closed behaviour in the production CityU path, even though this left integration incomplete. Testing provided evidence of progress while revealing the limits of automated verification. The AI offline suite expanded from 28 to 37 passing tests after nine CityU adapter tests were added. These covered blocked preflight, truncated responses, missing usage, metadata reset, and other failure paths. However, increased test coverage did not establish general model accuracy or a measurable reduction in defects because no formal defect-rate trend had been recorded. Reviewing the live evaluator also revealed that it could print a failed extraction comparison without making pytest fail. This demonstrated why human review must inspect assertions and failure conditions rather than trust a green test result. That correction remained outstanding and needed to be reported honestly. To keep artifacts aligned, I distinguished historical experimental evidence from production claims in the PR and documentation drafts. I also kept the shared data contract unchanged and followed fixed file-ownership paths, leaving cross-module consolidation to M1. These practices supported traceability, although the complete system still required integration checks for authorization, review routing, auditing, and case-state transitions. Preparing the memory and token-budget documentation also clarified which responsibilities belonged to the AI component and which depended on other owners. For example, holding text temporarily did not prove secure deletion, and returning an extraction did not prove that it was persisted or audited correctly. In future work, I would investigate provider capabilities earlier, define negative-test acceptance criteria before implementation, and associate evaluation results with exact code and prompt versions. I would also coordinate integration responsibilities sooner and preserve complete agent transcripts from the beginning. Overall, this experience showed me that responsible use of coding agents depends on human judgement about requirements, assumptions, and evidence. My contribution involved both implementing features and making their limitations visible so that the team could make informed decisions about readiness and remaining work.
